# Validating and storing Phone Numbers as E.164

Research note for issue #3 (part of #1, feeds #7). All sources fetched on 2026-11-11.

**Question.** How should Cadence validate and normalise a Phone Number typed into Settings so that what is stored is always E.164?

## 1. Which Node library: `libphonenumber-js` (vs Google's `google-libphonenumber`)

Is about `95 kilobytes`"; and `core`, "which doesn't come pre-packaged with any metadata". ### A number typed without a country code

- `parsePhoneNumber(string, defaultCountry?)`: "`defaultCountry: string` — Default country code for parsing numbers written in non-international form (without a `+` sign). Will be ignored when parsing numbers written in international form (with a `+` sign)." — README line 488 (2026-11-11)
- Without a default country a national-format number does not parse: `INVALID_COUNTRY` is raised "When parsing a non-international number without a `defaultCountry`: `parsePhoneNumber('(111) 222-3333')`" (for `parsePhoneNumberWithError`; the non-throwing `parsePhoneNumber()` returns `undefined`). — README lines 518-522 (2026-11-11)
- Same semantics upstream: `defaultRegion` is the "region that we are expecting the number to be from. This is only used if the number being parsed is not written in international format. The country_code for the number in this case would be stored as that of the default region supplied. If the number is guaranteed to start with a '+' followed by the country calling code, then RegionCode.ZZ or null can be supplied." `parse` throws "if no default region was supplied and the number is not in international format (does not start with +)". — `PhoneNumberUtil.java` lines 3165-3173, https://github.com/google/libphonenumber/blob/master/java/libphonenumber/src/com/google/i18n/phonenumbers/PhoneNumberUtil.java (2026-11-11)
- Lenient by default: "By default, the `extract` flag is `true` meaning that it will attempt to extract the phone number from an input string like `"My phone number is (213) 373-4253 and my hair is blue"`. ... To make it 'more strict', one could pass `extract: false` flag, in which case the function will attempt to parse the input string as if the whole string was a phone number." — README line 492; see also the "Strictness" section, line 537 (2026-11-11)
- IDD-prefixed input (e.g. `00 44 ...`) is also accepted when a default country is given: "`parseNumber()` will attempt to parse such IDD-prefixed numbers if 'default country' is provided". — README line 1452 (legacy API section, 2026-11-11)

### What "valid" means: possible vs valid

- In `libphonenumber-js`: `isPossible()` — "Only checks the phone number length. Doesn't check the actual phone number digits."; `isValid()` — "First checks the phone number length and then checks the phone number digits against all available regular expressions." — README, `PhoneNumber` section (2026-11-11)
- With the default `min` metadata the difference collapses: choose `min` when "You're fine with just validating phone number length via `.isPossible()` and you don't need to strictly validate phone number digits via `.isValid()`"; choose `max` when "The basic `.isPossible()` phone number length check is not enough for you and you need the strict phone number digits validation via `.isValid()`". — README lines 303, 309 (2026-11-11). The legacy-API section is blunter: "in the default configuration `isValidNumber()` performs absolutely the same 'lite' validation as `parseNumber()`" because "The precise regular expressions aren't included in the default metadata because that would cause the default metadata to grow twice in its size". — README line 1567 (2026-11-11)
- The author's recommendation ("Using phone number validation feature"): `isValid()` is "a double-edged sword in terms of how strict it is"; numbering plans change, so a site whose metadata is not updated "could get stale over time and start rejecting freshly-assigned phone number ranges"; "by using `.isValid()` in an application or on a website, you volunteer to keep it updated for the rest of its lifespan." The author prefers `isPossible()`. — README, "Using phone number validation feature" (2026-11-11)
- Upstream definitions. `isPossibleNumber` "returns true if the number is either a possible fully-qualified number (containing the area code and country code), or if the number could be a possible local number"; Google's README summarises it as a check that "quickly guesses whether a number is a possible phone number by using only the length information". `isValidNumber` "Tests whether a phone number matches a valid pattern. Note this doesn't verify the number is actually in use, which is impossible to tell by just looking at a number itself." — `PhoneNumberUtil.java` lines 2594-2600 and 2367-2373; https://github.com/google/libphonenumber/blob/master/README.md (2026-11-11)
- What "valid" does and does not promise: "A valid number range is one from which numbers can be freely assigned by carriers to users. Do not rely on libphonenumber to determine whether numbers are currently assigned to a specific user and reachable. Some products (e.g. Google 2-step verification) do this with a verification step e.g. by sending an SMS". — Google FAQ, "What does it mean for a phone number to be valid?" (2026-11-11)
- Length bounds: `TOO_SHORT` for "just 1 or 2 digits"; `TOO_LONG` "When the national (significant) number is too long (17 digits max) or when the string being parsed is too long (250 characters max)". — README lines 524-526 (2026-11-11). Upstream: "We support parsing and storing numbers from a minimum length of two digits to a maximum length of 17 digits currently (excluding country calling code). The ITU standard says the national significant number should not be longer than fifteen digits, but empirically this has been proven not to be followed by all countries." — Google FAQ, "What is the maximum and minimum length of a phone number?" (2026-11-11)

### Features `libphonenumber-js` deliberately drops (none matter for a Settings field)

Emergency numbers, SMS short codes, `*`-prefixed numbers, Australian `13` numbers, alphabetic numbers, "two-in-one" extensions, local numbers with the area code omitted, geolocation, `formatNumberForMobileDialing()`. — README lines 39-61 (2026-11-11)

## 2. How to pick the default country for parsing

- Both libraries need a region only when the input has no `+`; with a `+` the region is ignored (README line 488; `PhoneNumberUtil.java` line 3165-3169, both 2026-11-11). So the default country is a UX convenience for users who type a national number, not a correctness input for international ones.
- A fixed default is what Twilio's own Lookup does and it shows the failure mode: the `PhoneNumber` path parameter is "The phone number to lookup in E.164 or national format. Default country code is +1 (North America)." and `CountryCode` is "The country code used if the phone number provided is in national format." — https://www.twilio.com/docs/lookup/v2-api (2026-11-11). A Polish user typing `601 123 456` against a `+1` default would be silently turned into a North American number, so a fixed default should only ever be a last resort, never silent.
- What Cadence already has (from the codebase, not a web source): `resolveCountry(request)` in `app/lib/country.server.ts` returns an ISO-3166 alpha-2 code or `null` from (1) the DevUI session override, (2) the `CF-IPCountry` header, (3) an `ip-api.com` lookup; `purchases.country` in `app/db/schema.ts` is a nullable `text` column recorded at purchase time. The `users` table has no country column. `libphonenumber-js`'s `defaultCountry` takes exactly such a two-letter code (its `CountryCode` type; README line 488, 2026-11-11), so both are directly usable.
- Neither library documents a rule for choosing the default region; the Google Javadoc only says it is "region that we are expecting the number to be from" (line 3165, 2026-11-11). The choice is therefore a product decision; see the recommendation below.

## 3. Stored value vs displayed value

- E.164 is a first-class output of both libraries. `libphonenumber-js`: "`number: string` — The phone number in `E.164` format. Example: `"+12133734253"`." and `format('E.164')` → `"+12133734253"`. — README lines 583, 623 (2026-11-11). In source it is literally `this.number = '+' + this.countryCallingCode + this.nationalNumber`. — `source/PhoneNumber.js` line 68, https://github.com/catamphetamine/libphonenumber-js/blob/master/source/PhoneNumber.js (2026-11-11)
- Parsing canonicalises: "this method canonicalizes the phone number such that different representations can be easily compared, no matter what form it was originally entered in (e.g. national, international)". — `PhoneNumberUtil.java` lines 3156-3158 (2026-11-11). Google's FAQ: "when parsing, we remove a country's national or trunk prefix, so we can store a normalized form of the number." — FAQ, "Why wasn't the national prefix removed when parsing?" (2026-11-11). The Javadoc on `PhoneNumberFormat` adds: "If you are considering storing the number in a neutral format, you are highly advised to use the PhoneNumber class." — `PhoneNumberUtil.java` lines 468-469 (2026-11-11). Neither Google doc names E.164 as *the* storage format; E.164 is one of the enum's formats (`E164, INTERNATIONAL, NATIONAL, RFC3966`, line 471-475). For a SQLite text column, the E.164 string is the serialisation of that neutral form.
- Shape of an E.164 string, per Twilio's glossary: `+`, country code, national destination code, subscriber number; it must "Use decimal integers", "Be limited to a total of 15 digits in length", "Start with a `+`", "Exclude `0` as the first character as no E.164 country code starts with `0`"; "Country codes have a length between one and three digits." Examples `+14155552671`, `+442071838750`, `+551155256325`. — https://www.twilio.com/docs/glossary/what-e164 (2026-11-11). Google's source agrees on the ITU limit while deliberately exceeding it: "The ITU says the maximum length should be 15, but we have found longer numbers in Germany." (`MAX_LENGTH_FOR_NSN = 17`, `MAX_LENGTH_COUNTRY_CODE = 3`). — `PhoneNumberUtil.java` lines 62-67 (2026-11-11)
- ITU-T E.164 itself: title "The international public telecommunication numbering plan", current edition E.164 (02/26), approved 2026-02-13, status "In force". — https://www.itu.int/rec/T-REC-E.164 and https://www.itu.int/rec/T-REC-E.164-202602-I/en (2026-11-11). The ITU summary page says the Recommendation "provides the number structure and functionality for the eight categories of numbers used for international public telecommunication" and that "Annex A provides additional information on the structure and function of international public telecommunication numbers". — https://www.itu.int/dms_pubrec/itu-t/rec/e/T-REC-E.164-202602-I!!SUM-HTM-E.htm (2026-11-11). **Not found on a primary source in this session:** the ITU listing and summary pages do not state the 15-digit maximum or the CC + N(S)N definitions; the full PDF (https://www.itu.int/rec/dologin_pub.asp?lang=e&id=T-REC-E.164-202602-I!!PDF-E&type=items) downloaded but its text could not be extracted in this environment. The 15-digit figure above therefore rests on Twilio's glossary and Google's source comment, both of which attribute it to the ITU.
- Display formats. `format('NATIONAL')` → `"(213) 373-4253"`, `format('INTERNATIONAL')` → `"+1 213 373 4253"`; aliases `formatNational()` and `formatInternational()`. — README `format()` section (2026-11-11). International output uses "whitespace ... Instead of hyphens or brackets". — README line 57 (2026-11-11). Formatting rules are part of the metadata and change: "When does formatting in a country change?" — Google FAQ heading (2026-11-11); so a display string must be derived at render time from the stored E.164, not stored alongside it.
- For the input widget, the README also documents a `getNumberValue()` helper that "Returns the phone number in `E.164` format ... Will return `undefined` if no digits have been input, or when the user inputs a phone number in national format (without a `+`) and no default country or default 'country calling code' have been specified." — README line 947 (2026-11-11)

## 4. What a Twilio-shaped API expects on input

- Messages (SMS/MMS), `POST` create: `To` is "The recipient's phone number in E.164 format (for SMS/MMS) or channel address" (channel address example `whatsapp:+15552229999`); `From` is "The sender's Twilio phone number (in E.164 format), alphanumeric sender ID, Wireless SIM, short code, or channel address". — https://www.twilio.com/docs/messaging/api/message-resource (2026-11-11). The page does not say whether a non-E.164 `To` is rejected or normalised; **not found on a primary source**.
- Voice, `POST` create Call: `To` is "The phone number, SIP address, or client identifier to call." (no format stated on the request parameter); the Call resource's `to` property reads "Phone numbers are in E.164 format (e.g., +16175551212)." — https://www.twilio.com/docs/voice/api/call-resource (2026-11-11)
- Lookup v2 accepts national input only with an explicit `CountryCode` and otherwise assumes `+1` (quoted in section 2); it returns `phone_number` as "The phone number in E.164 format, which consists of a + followed by the country code and subscriber number", plus `national_format`, `valid` ("Boolean which indicates if the phone number is in a valid range that can be freely assigned by a carrier to a user") and `validation_errors`. — https://www.twilio.com/docs/lookup/v2-api (2026-11-11). Twilio's `valid` uses the same "freely assigned by a carrier" wording as Google's FAQ, i.e. it is libphonenumber-style validity, not reachability.
- Twilio's glossary: "To validate a phone number and its format, use the Twilio Lookup API" and "A regular expression (regex) can't guarantee a match with a valid number." — https://www.twilio.com/docs/glossary/what-e164 (2026-11-11)
- Net: a stored `+<cc><nsn>` string is exactly the `To` value Twilio Messaging documents; no conversion is needed at send time.

## What this means for Cadence

1. Use `libphonenumber-js` (MIT, zero deps, ESM+CJS, bundled `.d.ts`, metadata republished within days of Google's). Import from `libphonenumber-js/max` on the server so `isValid()` actually checks digits; the extra ~65 kB is server-only.
2. Validate on the server with `parsePhoneNumber(input, { defaultCountry, extract: false })`; reject when the result is `undefined` or `!isPossible()`; treat `!isValid()` as a hard reject too, since a dependency update every few weeks (Renovate/`npm update`) is the maintenance the README asks for.
3. Default country for national-format input: the Settings form pre-selects a country from, in order, the user's most recent `purchases.country`, then `resolveCountry(request)`; the user can change it. If no `+` and no country can be resolved, show "add your country code" rather than guessing. Never hard-code `+1`.
4. Store `phoneNumber.number` (E.164, e.g. `+48601123456`) in a new nullable `users.phone` text column, nothing else; the stored string is already what Twilio's `To` wants.
5. Display by re-formatting the stored value at render time: `formatInternational()` as the default (unambiguous across countries), `formatNational()` only when the viewer's country equals the number's.
6. Keep a uniqueness/equality rule on the E.164 string (`isEqual` compares `.number`), and expect the ~15-digit ITU bound but do not enforce it yourself; the library allows up to 17 NSN digits on purpose.
